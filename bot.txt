================================================================================
1. WHAT THE BOT IS
================================================================================

Kurisu is a Discord antinuke, raid-protection, ticket and moderation bot.

Main areas:
  - Antinuke with 28 configurable modules.
  - Nuke Guard: cross-module destructive-burst detection.
  - 24-hour nuke watch: a banned/kicked nuke executor is banned on sight.
  - Raid protection with levels, lockdown, verification mode and join history.
  - Whitelist for users AND roles, with per-module scopes.
  - Moderation commands and case/warning history.
  - Recovery: restore channels/roles, contain added bots, remove webhooks/
    invites, revert dangerous changes.
  - Verification panel with a public stable button.
  - Private support tickets with staff tools and optional log-only transcripts.
  - Cosmetic premium guild-member profiles (security is never gated).
  - Security Center (/security) and Command Center (/help), both Components V2.
  - Bot-network overview (/guilds), bot-owner only.
  - Prefix text commands using the same permission and V2 response pipeline.

Current scale:
  - 42 top-level slash commands.
  - 72 help entries (top-level commands + subcommands).
  - 28 antinuke modules.
  - 37 automated tests, all passing.
  - Version 2.1.0.

2. QUICK START / ENVIRONMENT
================================================================================

Install:
  npm install

Environment variables (.env):
  DISCORD_TOKEN   Bot token. Never commit it.
  CLIENT_ID       Discord application ID.
  DEV_GUILD_ID    Optional. Registers commands to one guild instantly.
  OWNER_IDS       Comma-separated bot owner user IDs. Always exempt, can edit
                  the whitelist, and are the only users allowed to run /guilds,
                  /premium and the owner-only security settings.
  DATABASE_URL    MongoDB connection string. Never commit or log it.
  DATABASE_NAME   Optional MongoDB database override. Defaults to the URI path,
                  then "prismo".
  DATABASE_PATH   SQLite file used only by scripts/migrate-sqlite-to-mongo.js.
  AUTO_DEPLOY     true = register commands on startup. Default false.
  LOG_LEVEL       debug | info | warn | error.

Startup:
  node index.js            (loads src/index.js)
  npm run deploy           (register slash commands)
  npm start                (production)

The database must be reachable before login. src/database/index.js connects,
pings, creates indexes, then runs one-time data migrations. Startup errors scrub
MongoDB credentials from the message.

3.2 VERIFICATION PANEL
  /verification panel channel:#verify [role:@Verified]
    - Posts a public Components V2 panel with button customId "kv:verify".
    - If no role is supplied, creates a permissionless "Verified" role.
    - Validates the role: not @everyone, not managed, no dangerous permissions,
      below Kurisu's highest role, and Manage Roles is present.
    - Re-posting replaces the old panel message and stores the new channel/id.
  /verification config
    - Shows panel state, role, verified-member count, account-age gate.
  /verification remove
    - Deletes the panel message and disables verification.

  Click flow:
    - customId is exactly "kv:verify"; every decision is re-read from MongoDB.
    - Wrong/inactive panel channel is rejected.
    - Already-verified members get an ephemeral notice before the cooldown check.
    - 5-second per-member cooldown (LIMITS.verifyCooldownMs).
    - Raid lockdown pauses verification.
    - Minimum account age comes from raid_config.min_account_age_days.
    - Grants the configured role and writes a "member" log entry.

3.3 TICKETS
  /ticket panel channel:#support
  /ticket setup [category:#tickets] [log_channel:#ticket-logs]
                [staff_role:@Staff] [max_open:3] [transcripts:false]
  /ticket close [ticket:12]
  /ticket add user:@member
  /ticket remove user:@member
  /ticket claim
  /ticket list [page:1]

  Custom IDs:
    kt:new:panel
    kt:close:<ticketNumber>
    kt:closeok:<ticketNumber>
    kt:cancel:<ticketNumber>
    kt:claim:<ticketNumber>

  Behaviour:
    - Ticket channels are private: @everyone denied View Channel; owner, staff
      role and bot receive explicit overwrites.
    - Ticket numbers come from an atomic per-guild counter.
    - max_open defaults to 3 and is enforced before channel creation.
    - Close requires confirmation; the ticket channel is removed after
      LIMITS.ticketDeleteDelayMs (10 seconds).
    - Transcripts are off by default. When enabled, a text transcript is sent
      only to the configured ticket log channel and is never persisted.
    - ticket_config and tickets are MongoDB collections with indexes.
    - Ticket channels are excluded from antinuke snapshots, automatic
      restoration and raid lockdown.
    - A manually deleted ticket channel cannot be recovered. The panel/setup
      views state this explicitly.

3.4 PREMIUM / PROFILE
  /premium enable [guild_id] [days]
  /premium activate [guild_id] [days]
  /premium disable [guild_id]
  /premium list [page]
    - Bot owner only. activate is an alias for enable.
    - /premium list is global and works outside a guild.
    - Every premium path acknowledges ephemerally before database or logging
      work, so slow Mongo/log delivery cannot cause an interaction timeout.
    - Premium rows have expires_at; expiry is enforced lazily by getPremium()
      and by an hourly/startup sweep.
    - Expiry removes the row and resets the cosmetic guild-member profile.
    - Premium never gates security, antinuke, raid or ticket features.

  /botprofile avatar|banner|reset|view
    - Premium guilds only; server owner / bot owner / Trusted Administrator.
    - Uses guild.members.editMe(), i.e. a guild-member profile, never the
      global bot avatar.
    - Accepts PNG, JPEG, GIF or WebP up to 8 MB; magic bytes are checked.
    - Stores only { avatar: 0|1, banner: 0|1 } flags in bot_profiles.
    - "view" is read-only and ephemeral.

5. SECURITY MODEL / ANTINUKE
================================================================================

Actors:
  - Guild owner: always exempt; cannot be punished.
  - Bot owners (OWNER_IDS): always exempt; cannot be punished.
  - Kurisu itself: always exempt.
  - Whitelisted users/roles: exempt according to level and scopes.
  - Administrator permission alone: NOT exempt. A Trusted Administrator also
    needs a trusted_admin whitelist entry.

28 antinuke modules:
  channelCreate, channelDelete, channelUpdate,
  roleCreate, roleDelete, roleUpdate,
  massBan, massKick, massUnban, prune,
  webhookCreate, webhookDelete, webhookUpdate,
  botAdd, guildUpdate,
  everyoneMention, massMention,
  permEscalation, integration, inviteSpam, massDelete,
  emojiDelete, stickerDelete, threadDelete, assetCreate,
  automodRule, vanityChange, nukeGuard

Hardened critical defaults (2.1.0):
  channelDelete    2 actions / 5s   -> ban
  roleDelete       2 actions / 5s   -> ban
  botAdd           1 action  / 60s  -> ban
  permEscalation   1 action  / 60s  -> ban
  automodRule      1 action  / 30s  -> ban
  vanityChange     1 action  / 60s  -> ban
  prune            1 action  / 60s  -> ban
  webhookDelete    3 actions / 20s  -> ban
  nukeGuard        3 actions / 10s  -> ban
  massBan          3 actions / 15s  -> ban
  massKick         3 actions / 15s  -> ban
  massUnban        3 actions / 15s  -> ban

Punishment fallback:
  ban -> kick -> quarantine -> strip dangerous roles -> timeout
  A ban requires no member fetch. If Discord refuses, each fallback is tried
  in order until one succeeds. A failed response releases the executor lock so
  a later action can retry.

Detection pipeline (hot path):
  1. GUILD_AUDIT_LOG_ENTRY_CREATE arrives with executor/target/changes.
  2. Duplicate audit entry IDs are dropped.
  3. Entries with no executor are ignored.
  4. Guild settings/modules/whitelist/watches/incident counts come from warm
     in-memory caches filled by repo.warmGuild().
  5. The action is classified into one or more modules.
  6. Exempt actors are skipped; Administrator alone is not exempt.
  7. Nuke Guard is evaluated across modules before per-module thresholds.
  8. The punishment call starts immediately. A ban is issued before mitigation
     and before any awaited persistence.
  9. Mitigation runs concurrently with the punishment: channel/role restores
     first, at most 3 tasks at once (RESTORE_CONCURRENCY = 3).
 10. Per-executor lock + already-punished set prevent double punishment. While
     locked, later actions are mitigated but not punished again.
 11. A durable 24h nuke watch is written after a ban or kick and is kept even
     while the executor is banned. A rejoin/action by a watched user bans them.
 12. Incident row + antinuke log line are written.

Bot-add containment:
  - The executor is banned first (botAdd default = ban).
  - The added bot is banned unless it has an explicit `bot` whitelist entry.
  - If the bot ban is refused: kick, then strip dangerous roles.
  - Integrations owned by the bot or executor are removed when available.
  - Invites created by the executor are deleted.
  - Trusted bots are skipped entirely.

Settings migration:
  - src/database/migrations.js removes only rows that exactly match the old
    shipped defaults for the hardened modules. Custom thresholds/windows/
    punishments/enabled flags survive.
  - Idempotent through the schema_migrations collection.
  - Adds compromised_guard: 0 to existing guild_settings rows without
    overwriting a value.

Compromised-account guard:
  - Default OFF, owner-only dashboard toggle.
  - When ON, whitelisted accounts younger than 7 days lose their whitelist
    exemption (LIMITS.compromisedMaxAgeMs).
  - Guild owners, bot owners and Kurisu remain protected.
  - Intended for freshly compromised throwaway staff accounts.

Nuke Guard:
  - Counts destructive actions across modules per executor.
  - Mixed bursts cannot stay below every individual threshold.
  - Burst state is mirrored to nuke_recent; memory is authoritative and the
    durable write is not awaited on the hot path.
  - Persisted rows are loaded once per guild at startup/GuildCreate.

Watch:
  - nuke_watch has a TTL index on expires_at_date.
  - The watch is re-created/refreshed to 24h when a watched executor acts.
  - It is not removed just because the executor is banned, so an unban cannot
    restore access silently.

Message modules:
  - everyoneMention and massMention run from messageCreate.
  - Nuke watch is checked there too.
  - Offending messages are deleted and deleted-message notes are recorded.

6. PERMISSIONS / AUTHORIZATION
================================================================================

  - isExempt / isExemptSync: guild owner, bot owner, Kurisu, whitelist levels
    and scopes. Administrator alone is not enough.
  - isExemptSync is the zero-I/O hot-path variant and reads warm caches only.
  - isTrustedAdmin: Administrator permission PLUS trusted_admin whitelist
    entry.
  - canManageSecurity: owner class or Trusted Administrator.
  - canGrantLevel: owner class can grant anything; Trusted Administrators may
    only grant trusted_mod and bot.
  - canRemoveEntry: owner protections cannot be removed.
  - isTrustedBot: explicit `bot` whitelist entry (or owner class).
  - accountTooNew: optional compromised guard, default off.
  - checkTarget: rejects self, Kurisu, guild owner, equal/higher roles and
    roles above Kurisu.
  - rolePosition/botMissing: hierarchy and permission diagnostics.

Whitelist scopes:
  - Stored as JSON array of module keys, ["*"] for all, or null for the level
    default.
  - Presets: pings/mentions, channels, channel-create, channel-rename,
    channel-delete, roles, members, webhooks, server, invites, messages,
    emojis, assets, threads, automod, bots, permissions, nuke.
  - Role entries are checked against member.roles.cache.
  - Entry scopes are ignored when no moduleKey is supplied (raid checks), so
    only fully exempt entries pass those checks.

Dashboard authorization:
  - Every component interaction calls canManageSecurity again.
  - Administrator-only members are rejected; only owner class or
    Trusted Administrators can open /security.
  - Premium is displayed read-only in Security Center.
  - The compromised-account guard toggle is owner-only.
  - Security navigation remains grey/secondary.

7. DATABASE / PERSISTENCE (MONGODB)
================================================================================

src/database/index.js:
  - MongoClient connect, ping, ensureIndexes(), then migrations.run().
  - Derives database name from the URI, DATABASE_NAME, then "prismo".
  - Redacts credentials from startup errors.
  - Exposes open(), get(), close(), ping(), info(), ensureIndexes().

Repository:
  - src/database/repo.js is async. Every caller must await.
  - Snowflakes remain strings; timestamps remain epoch milliseconds.
  - ObjectIds are never exposed to UI logic.
  - Atomic counters through counters.findOneAndUpdate($inc).
  - Warm caches for hot reads: guild settings, raid config, modules,
    whitelist, log channels, nuke watch, 24h incident counts, premium and
    verification. Writes invalidate/update the relevant cache.
  - _dropCaches() exists for tests.

Collections:
  guild_settings, antinuke_modules, raid_config, lockdown_channels, whitelist,
  warnings, mod_cases, incidents, log_channels, snapshots, recovery_log,
  quarantine, join_history, nuke_watch, nuke_recent, counters, verification,
  verification_users, ticket_config, tickets, premium, bot_profiles,
  schema_migrations

Important indexes:
  antinuke_modules  { guild_id, module } unique
  whitelist         { guild_id, user_id } unique
  log_channels      { guild_id, type } unique
  snapshots         { guild_id, kind, target_id } unique
  quarantine        { guild_id, user_id } unique
  nuke_watch        { guild_id, user_id } unique
  nuke_watch        { expires_at_date } TTL
  nuke_recent       { guild_id, executor_id, entry_id } unique
  nuke_recent       { created_at_date } TTL
  verification      { guild_id } unique
  verification_users{ guild_id, user_id } unique
  ticket_config     { guild_id } unique
  tickets           { guild_id, ticket_number } unique
  tickets           { guild_id, channel_id } unique
  tickets           { guild_id, state, created_at }
  tickets           { guild_id, owner_id, state }
  premium           { guild_id } unique
  premium           { expires_at }
  bot_profiles      { guild_id } unique

Persists across restarts:
  - guild config, module config, raid config
  - whitelist, warnings, moderation cases, incidents
  - log channels, snapshots, quarantine, join history
  - lockdown state, nuke watch, recent Nuke Guard burst window
  - verification panels and verified-user records
  - ticket config and ticket records
  - premium rows and profile flags

In-memory only:
  - antinuke sliding windows
  - audit-entry dedupe cache
  - per-executor punishment locks and already-punished set
  - early-watch alert dedupe
  - verification click cooldown

TTL indexes are not immediate. Code still filters expiry when reading.

10. RULES / DO NOT BREAK
================================================================================

  - Components V2 only. No embeds, no accent colours, no non-secondary buttons
    (except explicit link buttons where the existing design uses one).
  - No Unicode emoji in user-facing text or source. Use the registry.
  - Do not invent emoji IDs. A missing key must be reported, never replaced
    with a Unicode fallback.
  - Re-authorize EVERY component interaction from the database. Never trust
    customId for permissions or target identity.
  - Administrator permission alone never gives antinuke immunity.
  - Trusted Administrators cannot disable antinuke or raid, cannot grant
    bypass/trusted_admin, and cannot remove owner protections.
  - Owner protections (guild owner, bot owner, Kurisu) stay intact.
  - Do not add a security feature that is gated by premium.
  - Do not expose /guilds or /premium to non-bot-owners.
  - Do not add GuildPresences without a portal change and a clear reason.
  - Do not assume "k" is the default prefix. Default is "!".
  - Do not commit .env, tokens, DATABASE_URL, MongoDB data files, SQLite files
    or the local zip. Do not paste an Atlas URI into source, logs, README,
    bot.txt or commits.
  - Keep one commit per task. Do not mix unrelated changes.
  - Keep tests green and add coverage for every new feature.


================================================================================
11. KNOWN LIMITS / RISKS
================================================================================

  - Discord cannot restore messages from a deleted channel.
  - Restored channels/roles get new IDs; deleted-role members are not
    re-assigned.
  - Server icon, banner and vanity URL cannot be restored through the API.
    Kurisu restores the server name only.
  - Restored roles and overwrites never regain dangerous permissions.
  - Reverting a role edit only removes newly added dangerous permissions.
  - Mass message deletion relies on bulk-delete audit entries; Discord merges
    individual moderator deletions, so counts are approximate.
  - Quarantine uses removed roles, a permissionless role and a 28-day timeout.
  - Lockdown uses verification level, @everyone send permissions and invite
    pause; it never mass-bans.
  - Message logs show metadata, not content.
  - Manually deleted ticket channels cannot be recovered. Transcripts must be
    enabled in advance and go only to the ticket log channel.
  - The animated `ticket` emoji must be visible to the bot; startup validation
    reports it if Discord cannot resolve the registered ID.
  - MongoDB TTL cleanup is not instantaneous; code filters expired rows.
  - Warm caches assume the bot process is the only writer. External DB edits
    require a restart or cache invalidation.
  - The SQLite importer is legacy; do not run it against a live production
    database without a backup and dry run.
